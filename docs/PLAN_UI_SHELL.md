# 规划 v2：单场景 UI —— 以基地骨架为准

> **本版替换 v1（五等分槽位）。**
> v1 把日志拉成整条 640×54 底栏、把经济 HUD 拉成整条 640×26 顶栏、把左栏拉成 88×280 通高。
> 那不是"保持基地结构"，那是另起一套骨架，然后要求基地去适配它——等于把基地界面重排一遍。
>
> v2 反过来：**基地的七个区域一个像素都不动，探索和战斗往里填。**
> 前置调研：`docs/RESEARCH_SINGLE_SCENE.md`
> 基准：640×360（四份 CanvasScaler 实测一致：`ScaleWithScreenSize` / `Expand` / `match 0.5`）

---

## 0. v1 → v2 到底改了什么

| 项 | v1（上一版） | v2（本版） |
|---|---|---|
| 骨架来源 | 自行五等分 | 基地既有七区 |
| 顶栏 | 整条 `640×26` 经济条 | 左上角 `170×74` 原 HUD |
| 日志 | 整条 `640×54` 底栏 | 右下角 `150×124` 原日志位 |
| 左栏 | `88×280` 通高 | `84×124` 原左栏位 |
| 内容区 | 单块 `552×280` | 舞台 `270×170` + 侧栏 `170×160` |
| 底带 | 没有（被并进内容区） | `398×132` 工作台带，三模式恒在 |
| 基地面板改动 | 五个面板全部要挪 | **0 处**（左栏内容除外） |
| 战斗敌人 | 3 张 170×126 全卡 | 1 张焦点卡 + 侧栏 3 行 |

**放弃 v1 的两个好处，明说**：日志从 640 宽变回 150 宽（容量降约一半）、内容区从 552×280 缩到 270×170。换回来的是基地零改动和一条强得多的连续性线索（见 §3.3）。

## 1. 原则：基地是骨架，不是素材

1. **基地既有面板的 `rect` 是常量**，本次除左栏内容外一律不碰。它们就是三种模式共用的"房间"。
2. **新模式的新元素必须"投递"进既有区域。** 投递不进去，说明该元素不该出现，而不是区域需要变大。
3. **区域角色固定，内容可变。** 判断某个元素该放哪儿，先问"它在基地里属于哪个角色"，不按坐标找空位。

第 3 条是这次重写的核心。v1 是"哪块空就往哪块塞"，v2 是"先认角色，再落位"。

## 3. 区域角色契约

### 3.1 七区 × 三模式

| 区 | 角色 | 基地 | 探索 | 战斗 |
|---|---|---|---|---|
| **A** 账本 | 长期压力 | 周·天 / 应缴·已缴 / bit / 债务条 | 同左 | 同左 |
| **B** 主行动条 | 唯一的"离开当前状态" | 出征 | 执行 | 结束回合 / 搜刮全部 |
| **C** 舞台 | 焦点：正在看的那件事 | 立绘 + 台词 | 地点 + 叙事 + 已选行动 | 焦点敌人全卡 + 意图 |
| **D** 侧栏 | 可选项清单 | 8 设施页签 + 内容 | 行动袋（6×4） | 敌人列表（3 行） |
| **E** 状态 | 我这具身体 | 生命 / 能量 / 背包 / 仓库 | 生命 / 能量 / 警戒 / 阶段 | 生命 / 能量 / 护盾 / 护甲 |
| **F1** 背包 | 随身容器 | 6×5 | 6×5 | 6×5 |
| **F2** 中段大板 | 当前上下文的大面板 | 仓库（可滚动） | 结果预估 / 结算 | 焦点敌人背包 |
| **F3** 保险箱 | 死亡不掉落 | 2×2 | 2×2 | 2×2 |
| **G** 日志 | 发生了什么 | LOG | LOG（连续） | LOG（连续） |

### 3.2 为什么这个映射成立

不是硬凑，四条都有实测依据：

1. **D 区在基地就是"页签 + 竖排内容"**（8 个 20px 页签 + `170×138` 内容区）。而探索的行动列表、战斗的敌人列表，本来就是"竖排可选项"。同一个角色，只是项数从 8 变 5 变 3。
2. **F2 的宽度是 184、高 124**，而探索的「结果预估」面板实测就是 `184×112`——尺寸几乎一模一样。这不是巧合，是因为两者都是"一块放长文本/大图的大板"。
3. **C 区的立绘位（84×84，局部 `(-58,-32)`）** 在探索里正好装下已选行动袋 `4×3 = 64×48`，在战斗里正好装敌人立绘。基地留出的这个方形空位，天生是"放一个实体"的位置。
4. **战斗逻辑里已经有 `_selectedEnemy`**（`:87`），点击敌人面板会赋值（`:256`），选中面板换底色（`:616`），`CurrentTarget()` 读它（`:1462`）。**"焦点敌人"这个概念代码里已经有了，只是 UI 把三张卡全摊开、没有把它做成"焦点"。** §5 就是把这个既有概念显式化。

### 3.3 这次"看起来是一个场景"比 v1 强在哪

v1 靠"顶栏底栏整条不动"制造连续感，那是**装饰性**的连续：玩家不会盯着顶栏看。

v2 靠四件玩家真正会碰的东西连续：

| 锚点 | 为什么强 |
|---|---|
| **F1 背包 + F3 保险箱是同一份数据、同一个 `BagView` 实例、同一个位置** | 玩家的物品在三种模式下**物理上没动过**。拖到一半切模式，东西还在光标下 |
| **G 日志在右下角同一处连续追加** | 进入战斗能看到上一秒在探索里发生了什么，不用切回去查 |
| **B 主按钮固定在右上** | 「出征」→「执行」→「结束回合」，同一位置同一尺寸，肌肉记忆不用重建 |
| **E 的左下角永远是生命/能量** | 危险感有固定坐标 |

第一条是决定性的。v1 把背包放进内容区，切模式时背包会被销毁重建——**玩家最在意的格子会消失一次**。v2 里它属于外壳，永不重建。

### 3.4 归属划分（代码层面的硬边界）

**外壳持有（Screen 无权创建/销毁）**：A、B、D 的页签行、E、**F1**、**F3**、G
**Screen 只能往三个洞里建东西**：C（舞台）、D 的内容区、F2（中段大板）

```csharp
public sealed class ScreenSlots
{
    public RectTransform Stage;       // C，270×170
    public RectTransform SideContent; // D 内容区，170×138
    public RectTransform BenchMid;    // F2，184×124
}
```

Screen 拿不到 Canvas、拿不到 F1/F3、拿不到 A/E/G。想改它们只能调壳的接口：
`Chrome.Refresh(ChromeModel)` / `Chrome.AppendLog(string)` / `Chrome.SetAction(...)` / `Chrome.SetTabs(...)`。

## 5. 关键决定：战斗从「三张全卡」改成「一行一焦点」

这是本版唯一改变操作感受的地方，单独说明。

### 现状

3 张 `170×126` 全卡横排在 `(-185 + i×190, 105)`，铺满 640 宽，每张卡里塞了名称、血量、血条、4×3 背包格、AP、意图、护甲。点哪张卡就 `_selectedEnemy = i`。

### 为什么在基地骨架里放不下

C 区舞台只有 270 宽。3 × 170 = 570，超出一倍。
压到 86 宽/张能塞进 270，但 4×3 背包格就要占 64 宽——卡里没地方放名字和意图了。

### 新做法

| 层 | 承担 |
|---|---|
| D 侧栏 3 行 | 名称 + 血量 + 血条 + 意图**简写** → 三敌态势一眼扫到 |
| C 舞台焦点卡 | 当前目标的全部细节 + 意图**全句** |
| F2 中段 | 当前目标的背包（4×3 完整格） |

### 代价与退路

- **代价**：看某个敌人的完整信息要点一下；同时观察三个背包做不到。
- **退路**：如果试玩后认为"必须同时看三张卡的意图"，把 C 区 270 宽三等分（86 宽/卡，只留名称 + 血条 + 意图图标），D 侧栏改「战利品」页签。背包已经在 F2 了，所以 86 宽只放三行信息是够的。**这个退路不需要改外壳。**
- **不需要新的逻辑**：`_selectedEnemy`、`CurrentTarget()`、选中高亮、`HasFled` 判定全部复用。唯一新增的是一个 `IntentShort(enemy)` 派生函数（从既有 `IntentFor()` 里取关键词：攻击/治疗/防御/撤离 + 数值）。

### 7.1 三条硬约束

1. `ScreenSlots` 里只有 `Stage` / `SideContent` / `BenchMid` 三个字段。**没有 Canvas、没有 F1、没有 F3、没有 A/E/G。**
2. 配色只能从 `UiTheme` 取。删掉三个 Bootstrap 里的 `static readonly Color`，编译期就不可能再漂移。
3. `ShellRegions` 的 7 个 rect 是 `const`。

### 7.2 F1/F3 上提是本方案的技术核心

现状：三个 Bootstrap 各自 `_bag = GameSession.PlayerBag` + `BuildBagPanels` 各自建一份 `BagView`。
上提后：`BenchSlots` 建一次，`GameShell` 生命周期内唯一。

风险点：`BagView.Initialize` 需要 `_palette` 与 `_catalog`。这两个都是全局的（`GameSession.Catalog` + `BuildPalette`），所以上提没有额外依赖——但**必须在 Step 1 里一次性做完**，否则基地会短暂出现两份背包，拖拽会串。

## 实施记录 · Step 3：战斗压栈

### 外壳：屏幕栈

```csharp
var screen = shell.PushScreen("Combat");   // 隐藏当前屏，新开 B/C/D/F2 四个容器
screen.Region(ShellRegionId.Stage)          // 战斗往这里建 C 区
```

### 探索侧

```csharp
private void EnterCombat()
{
    if (_containerWindows != null) _containerWindows.CloseAll();
    gameObject.SetActive(false);                        // 静默自己这一侧所有 Update
    CombatPrototypeBootstrap.Launch(_shell, OnCombatExit);

```

`gameObject.SetActive(false)` 而不是 `enabled = false`：探索的拖拽、弹窗、浮窗分散在多个组件上，
关 GameObject 一次全停；退出回调是普通委托，不受激活状态影响。

| 出口 | 数据 | 回到哪里 |
|---|---|---|
| Looted（打赢 + 搜刮完） | `CompleteEncounter(hp)`：生命写回、`EncountersCleared++` | 弹栈回探索，刷新后继续 |
| Retreated（撤离 / 敌人逃离） | `RetreatEncounter(hp, fled)` | 弹栈回探索 |

### 两个必须记住的坑

1. **`Launch` 里必须显式调 `Initialize()`，不能等 `Start()`。**
   压栈是在别的组件的调用栈里发起的，此时 Unity 可能把新组件的 Start 推迟到场景切换之后，
   结果就是"组件挂上了、界面一个控件都没有"。现在 `Start()` 只是 `Initialize()` 的兜底，
   靠 `_initialized` 防重。
2. **Unity 编辑器在窗口失去焦点时会停住 Play 循环**（`Time.frameCount` 不前进）。
   这时反射调用任何"下一帧才生效"的逻辑都会拿到 null 字段，容易误判成代码 bug。
   可靠的推进方式：`EditorApplication.isPaused = true; EditorApplication.Step() × N; isPaused = false;`。
   副作用是 Job 系统会刷一串 `JobTempAlloc` 警告——那是单步推进造成的，不是游戏代码的问题。

### 仍未解决

基地 → 探索 仍是 `LoadScene("ExpeditionPrototype")`，`GameShell` 随场景重建，F1 的 `BagView` 实例会换掉。
"拖到一半切模式、物品还留在光标下"这条只有把基地也搬进同一个场景才能过——即 Step 4。

## 实施记录 · Step 4：单场景（基地也在栈里）

**目标**：`基地 → 探索` 不再 `LoadScene`，三模式变成同一个场景里的三层；删掉 `CombatPrototype` /
`ExpeditionPrototype` 两个场景。原先"拖到一半切模式、物品还在光标下"这条过不了，就是因为基地↔探索
还在换场景——外壳连同 `BagView` 一起重建，`InstanceID` 必然变。

### 最终结构

```
ScreenLayer
├─ Region_Primary / Stage / Side / Dock      默认屏（Step 1 建的，现在只当占位）
├─ Screen_Base                              基地整屏（基地自己建的四块都在里面）
├─ Screen_Expedition_Primary/Stage/Side/Dock 探索压的第一层
└─ Screen_Combat_Primary/Stage/Side/Dock     战斗压的第二层
   ＋ Band_Battlefield / CombatMessage       战斗的跨区带与播报行（Step 3 加的，挂 ScreenLayer）

栈深：1 = 基地　2 = 探索　3 = 战斗
```

A 账本 / E 左栏 / F1 背包 / F3 保险箱 / G 日志不入栈，三层共用同一批控件——这是"看起来是一个场景"
以及"背包里的东西一直在原处"的物理保证。

### 三处改动

| 文件 | 改动 |
|---|---|
| `BasePrototypeBootstrap` | 基地内容建在 `_baseScreen`（整屏容器）里；`Deploy()` 变成 `SetBaseVisible(false)` + `gameObject.SetActive(false)` + `ExpeditionPrototypeBootstrap.Launch(...)`；新增 `OnExpeditionExit` 恢复并 `RefreshAll()` |
| `ExpeditionPrototypeBootstrap` | 新增 `Launch/Initialize/Exit/TearDown` + `ExpeditionExit{Completed,Defeated,Aborted}`；三处 `LoadScene("BasePrototype")` 改成 `Exit(...)`；建 UI 从 `_shell.Region(...)` 改为 `_screen.Region(...)` |
| `CombatPrototypeBootstrap` | 只有 Defeated 那条出口的行为变了：不再 `LoadScene`，而是回调探索 → 探索 `Exit(Defeated)` → 基地 |
| `SettingsOverlay` | `CanSaveNow()` 从"场景名 == BasePrototype"改成"栈深 ≤ 1" |
| `GameShell` | `OnDestroy` 清空 `Instance`（回主菜单后重开档案要用） |
| `Scenes/` | 删除 `CombatPrototype.unity`、`ExpeditionPrototype.unity`；`EditorBuildSettings` 只留 MainMenu + BasePrototype |

### 四个坑（都是实测踩出来的）

1. **压栈那一帧的点击会漏到新一屏。**
   「出征」(455,14,160,28) 和「执行」是同一个矩形。基地的 `Update` 处理完这次按下、立刻拉起探索，
   同一帧里探索的 `Update` 也看到 `wasPressedThisFrame == true`，于是刚进探索就自己执行了一次行动。
   三处 bootstrap 都加了 `_ignoreInputUntilFrame = Time.frameCount`，`Update` 首行判掉。
2. **基地的内容必须包在一个整屏容器里。** `PushScreen` 只隐藏"自己的那一屏"（四个区域容器），
   基地当初是直接铺在 `ScreenLayer` 上的，压栈后压根收不掉——探索会和基地叠在一起。
   现在 `_baseScreen` 是一个 640×360 的透明容器，`SetActive(false)` 一次收干净。
3. **`Destroy` 在 `isPaused = true` + `EditorApplication.Step()` 下不执行。**
   验证时一度看到"弹栈后敌人卡还在、depth 已经是 1"，误判成清理没生效。
   真相是暂停单步不会跑到帧末的销毁阶段。**放松 `isPaused`、让真实帧过去再查**，一切正常
   （`combatN=0 expN=0 depth=1`）。这条和 Step 2 那条"失焦停帧"是同一类假象。
4. **`GameShell.Instance` 必须在 `OnDestroy` 里清空。** 回主菜单（`LoadScene("MainMenu")`）会销毁外壳，
   但静态字段还指着已销毁对象；再点开始游戏时 `Ensure()` 直接返回那个空壳，表现为"什么都没建"。
   实测：MainMenu 时 `shellNull=True`，再进基地 `shellNull=False`、`depth=1`、`Screen_Base` 在。
